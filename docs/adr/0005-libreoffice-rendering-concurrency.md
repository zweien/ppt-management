# ADR-0005:LibreOffice 渲染并发 —— 多容器单并发 + 常驻保活

- **状态**:已接受
- **日期**:2026-07-29
- **决策者**:工程讨论确认
- **取代**:无

## 背景

LibreOffice Headless 不是为并发设计的:

1. **单进程内串行**:同一个 LO profile(由 `-env:UserInstallation=file:///path` 指定的用户配置目录)同时只能跑一个转换任务,第二个会被锁阻塞。
2. **进程启动慢**:冷启动 `soffice --headless` 需 1–3 秒,每次任务都 fork 新进程的话,40 页 PPT 的吞吐会被启动开销吃掉。
3. **僵尸/泄漏**:LO 跑久了会留孤儿进程、锁文件残留,需要监控和清理。

PRD §19.2 写"LibreOffice 每 worker 单并发或低并发",§17.2 把 `worker-render` 列为一个服务,但没定义 worker 内部如何并发。

## 决策

### 并发模型:多容器单并发

**每个 `worker-render` 容器内只跑 1 个 LO 任务**(单 profile、串行),靠**多起容器**扩并发:

```yaml
worker-render:
  deploy:
    replicas: 2   # 起步副本数,观察队列堆积再扩
  restart: unless-stopped
```

Celery 自动在副本间负载均衡。

### 常驻保活

worker 启动时拉起一个常驻 `soffice --headless` 进程(单 profile),后续任务复用它(单进程内排队串行),避免冷启动开销。

### 容错

- 单页渲染超时 60s。
- LO 进程崩溃 → 容器 `restart: unless-stopped` 自愈 → 任务靠幂等键回队列重试。
- 锁清理:容器重启天然清理本 profile 目录下的 `.lock` 残留。

## 理由

**选多容器单并发(B),而非单容器内进程池(A)**:

1. **容器级隔离**:一个容器里 LO 崩溃/泄漏/锁残留只影响它自己,重启一个容器即可,不污染整个 worker 层。LO 僵尸进程是这类系统的头号运维噩梦,容器化隔离是最省心的解法。
2. **与 Docker 部署形态契合**:就是 `replicas`,无需自写进程池管理器。
3. **LO 单 profile 串行约束变成特性**:本来就只能单并发,那就每容器单并发,数量上扩。
4. **容量匹配**:PRD 假设 500 份 × 40 页 ≈ 2 万页是一次性入库量,2 副本 / 每页 3–5s ≈ 8–14 小时跑完,可接受。

**常驻保活缓解 B 的唯一短板(冷启动)**:单容器串行时可保活一个常驻 soffice 复用,比每次 fork 快,又保留容器隔离。

## 后果

- **正面**:运维简单(容器自愈、锁自动清理);隔离性强;无需进程池管理器代码。
- **负面**:容器数 = 最大并发数,扩容靠加副本/加机器;单机内并发密度不如进程池方案(但 MVP 规模足够)。
- **迁移成本**:若未来容量暴涨到几十万页需极高吞吐,可迁移到单容器进程池(A),迁移成本不高(都封装在 worker 任务函数内)。
