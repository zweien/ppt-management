# ADR-0002:单页 PPTX 导出 —— 关系图遍历 + 复制或拒绝

- **状态**:已接受
- **日期**:2026-07-29
- **决策者**:工程讨论确认
- **取代**:无

## 背景

PRD §11 要求支持"导出单页 PPTX":用户从某份 PPT 中选取一页,得到一个**只包含该页**、且**所有原生对象(文字、形状、图片、图表、母版)保持可编辑**的新 PPTX。

PRD 给出三条硬约束(§11.1):

> **禁止重建页面** —— 单页导出不经过 LibreOffice 保存,不把页面转成图片,也不使用 python-pptx 重绘。系统直接复制源 PPTX 中的页面 Open XML 部件及其依赖关系。

但 PRD 没有定义三个工程细节,而这些细节一旦到阶段三才定,会反向影响数据模型与对象存储布局:

1. 依赖复制**递归到哪停**?
2. 复制失败时**降级策略**是什么?
3. 校验的**阈值与方法**用什么?

## 决策

### 1. 终止规则:内部关系图遍历 + visited-set 防环

从目标 `slide` 出发,解析其 `.rels`,对所有 `TargetMode != External`(即 Internal)的 relationship 做 BFS/DFS 遍历,用 visited-set 防环,**凡是内部可达的 part 全部复制**。对 `TargetMode=External`(超链接、外部链接工作簿、链接型 OLE)**保留 relationship 引用但不跟随复制**。

**不按对象类型写白名单**(不写"复制 chart 的 xlsx、复制 smartArt 的 4 个 part…"这种逐类型清单)。

### 2. 失败策略:复制或拒绝,绝不静默降级(方案 A)

- 图遍历能复制的内部 part 都复制(包括 OLE、SmartArt、嵌入 xlsx 等)。
- 渲染校验不过 → **拒绝导出**,在 `export_files.validation_status` 记录失败,向用户报告**具体失败对象类型 + 日志编号**。
- **绝不**把对象转成图片嵌回(方案 B 的"标记后转图降级"),因为那违反 §20.3"形状/图片/图表仍为原生对象"的验收,且对用户有欺骗性。
- 例外:未嵌入字体**永不阻断**(字体替换是 PPTX 通病,无法嵌入手里没有的字体),最多在导出说明里提示。

### 3. 校验方法:同管线现渲 + 硬属性前置 + pHash 双档

**关键约束**:绝对不能用上传时缓存的预览图来对比(中间 LibreOffice 版本/参数可能变过,比的是两张本就该不同的图)。必须**把源 slide 用同一条渲染管线现渲一次,再和导出页现渲一次比**。

分层校验:

- **廉价硬检查(先做,布尔判定)**:导出 PPTX 恰好 1 页;slide 尺寸(EMU)与源一致;`[Content_Types].xml` 无悬空引用。失败直接拒。
- **图像层**:64-bit 感知哈希(pHash)+ Hamming distance,部署级可配阈值:
  - `distance ≤ 8` → 通过(覆盖抗锯齿抖动)
  - `9 ≤ distance ≤ ~20` → 仍交付,标记"待复核"
  - 远大于阈值(结构大变,如一空一满) → 拒绝

## 理由

**终止规则用图遍历而非类型白名单**:

- PPTX 包是有限且基本无环的,visited-set 保证终止。
- chart→嵌入 xlsx 这种 PRD 担心"递归到哪算必要"的 case,在图遍历里**自动处理**——xlsx 是 `/ppt/embeddings/` 下的内部 part,被 chart 的内部 relationship 引用,自然被拷进来,无需特例。
- 新对象类型(没见过的 OLE/第三方插件)会被正确包含或正确识别为风险,而不是被白名单默默漏掉。代价仅是需正确解析 `.rels` 并区分 Internal/External,这本就是解析层必备能力。

**失败策略选 A 而非 B(转图降级)**:

- B 的"局部转图"违反 §20.3 可编辑性验收,且对用户有欺骗性(拿到文件以为能改,关键部分是死图)。
- A 的"拒绝 + 报告对象类型"诚实且可观察,符合 PRD 既有的容错哲学(类似 MinerU 失败不阻断基础检索,这里是导出失败不输出坏文件)。

**pHash 双档而非像素级比较**:

- LibreOffice 渲染本身有抗锯齿抖动,像素级比较不现实。
- pHash 双档既放过正常抖动(≤8),又对可疑结果(9~20)留下"待复核"标记,不误杀也不放过结构大变。

## 后果

- **正面**:导出算法边界清晰;导出的页面永远是原生对象(满足可编辑性);失败可观察、可重试。
- **负面**:遇到 SmartArt / OLE / 第三方插件这类环境相关对象时,部分页面会导出失败并需用户感知(但这是诚实的失败,优于静默产出坏文件);pHash 阈值需在真实样本上标定。
- **数据模型影响**:`export_files.validation_status` 需支持 `passed` / `pending_review` / `failed` 三态,`error_code` 需能记录失败对象类型。
